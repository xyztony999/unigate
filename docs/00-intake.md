## 2. 拟议产品定位

已确认定位：单一主办方自托管的报名与入场管理系统，支持多场活动，以大学见面会作为需求来源，首版按单场 500 人以内设计（含随行者）。

提供两种业务使用路径：

1. 完整路径：创建活动 → 参与者报名 → 获得入场凭证 → 现场检票 → 统计及数据清理。
2. 检票路径：创建检票活动 → 导入外部名单 → 校验与处理冲突 → 准备入场识别方式 → 现场检票 → 导出结果。

“独立检票”现已明确：可不使用内置报名，由后台配置及导名单后，Android 在现场断公网、保留局域网时完成检票统计；不要求 Android 单机从零替代后台（ADR-031）。

## 3. 需要优先澄清的范围

首问已回答：用户选择方案 1，首版为单一主办方自托管、支持多场活动，完整报名与外部名单检票均可使用。多机构公共 SaaS 不进入首版范围。

同组共用码、分批单次核销。局域网 Android 主备协调；境内活动及后台，海外明细账号查看及境内导出。文件及飞书问卷/腾讯文档 API 接入，先个人测试并保留组织接入。字段、发码、短信验证及报名后修改取消均按活动配置；容量按总人数、待审核不占额。单场 500 人以内、2–5 台，人工/自助均需，现场加人补录仅负责人。页面及邮件领票，明细默认活动后 30 天可配置。Spring Boot 与 Vue。当前集中确认：独立准备边界、现场云端写入和外部名单审核。

沟通偏好：用户要求后续统一选择题、加快推进；同阶段关键项合并提问，常规实现细节由设计草案集中审阅。

原始待澄清主题如下；用户最新要求后续采用选择题并加快，当前按关键项分批集中选择：

1. 参与者与操作者：家长、学生、同行人、志愿者、活动负责人及校方的数据使用职责。
2. 随行规则：是否允许同一家人分批到场；本人不在场时同行人能否先入场；是否需要逐人票证。
3. 检票独立性与网络：无内置报名、无公网但有局域网、单设备完全离线、多设备完全隔离分别是否需要支持。
4. 首发地区及主办主体：活动地点、服务器地区、个人信息处理职责、海外管理人员的访问方式。
5. 导入：优先支持的平台、是否能提供脱敏样例、仅文件导入还是调用平台 API。
6. 规模与设备：单场报名量、入场峰值、入口数量、手机及平板系统、自助或工作人员操作。
7. 报名身份与找票：手机号是否必要、是否验证、无手机号或国际号码如何处理、丢失票证如何恢复。
8. 技术栈与部署维护：结合开发者熟悉程度决定，不因引擎附带某种技术栈而直接选用。

## 4. 建模时必须覆盖的问题

### 随行人数与实际到场

建议在概念上区分报名组、报名联系人、入场名额、检票事实与调整记录，不预设只需三张表。

需要分别定义报名组数、计划到场人数、实际入场人数、剩余可入场人数，以及有无离场统计。没有离场记录时，累计入场人数不能展示为当前在场人数。

示例：一组预登记 3 人，先到 2 人，稍后再到 1 人。若支持此场景，检票不能只有“未签到/已签到”两个状态，也不能在首次扫码时直接把全部 3 人计入实际到场。

如只收随行人数而不识别具体同行者，系统最多能可靠管理组内名额与数量；无法据此证明每个具体的人是否重复入场。

### 多设备及离线

在线核销需要服务端原子判断名额与幂等处理，避免重复点击或请求重试重复计数。

在设备完全互不通信时，不能保证同一凭证在多个入口只放行一次。可讨论单一离线入口、按入口分配凭证、共享局域网服务，或接受风险并在同步后报告冲突。同步后的冲突提示无法撤回已经发生的现场放行。

离线设计还需覆盖名单版本、临时新增、撤销凭证、设备时间不可信、重复上传、丢失设备及本地个人信息清理。

### 外部名单与身份

建议首版从 CSV/XLSX 字段映射、导入预览、逐行错误和人工冲突处理开始，平台 API 连接器待具体需求确认后决定。

手机号可以作为候选匹配线索，不能默认作为跨活动、跨来源的人员唯一标识。家庭共用联系方式、空手机号、号码更换、来源语义不同都可能导致误合并。外部平台二维码也不能默认由 UniGate 直接识别，需要确认格式、验真方式或重新发放凭证。

手机号后四位只适合作为工作人员辅助检索线索；不能用于公开找回完整票证或暴露报名名单。

### 现场设备

需区分工作人员持机检票与参与者自助终端。自助终端不应开放名单搜索、完整联系方式或管理操作，完成后应自动清屏。

PWA 的全屏展示与设备锁定属于不同层次。真正限制退出、切换应用及恢复运行，需要根据平板系统选择设备级管理方式。持久存储、重启及会话重置也需在目标设备上验证。

### 数据职责

正式设计需明确数据用途、必要字段、告知及适用的合法处理基础、访问权限、导入来源授权、保留与删除、导出审计、备份恢复，以及主办方与部署维护者的职责。

将报名页面称为“家长报名”并不能替代对实际收集内容和参与人群的判断。学校采购所需的安全评审、合同和部署要求，应向目标学校确认，不预设统一清单。

海外校方获取报名明细已是明确需求（ADR-010）。官方第二版指南把境外机构可查询、调取或下载境内数据列为出境场景，因此远程查看和文件交付都需纳入数据流分析，不能以“不下载”或“境内服务器”直接排除。具体适用机制需结合实际主体与数据确定，告知、适用同意及影响评估等要求应进一步核对。[第二版指南](https://www.tjcac.gov.cn/wsfw/sjkj/zcfgsj/202408/t20240823_6705580.html)、[跨境流动规定](https://www.cac.gov.cn/2024-03/22/c_1712776611775634.htm)

## 5. 已核实的参考与对既有讨论的修正

以下为 2026-10-20 查询到的官方项目资料及主管部门资料，不是穷尽式选型，也不构成对未来上线的合规结论。

- **pretix 值得作为基线比较。** 官方 pretixSCAN 文档覆盖人工查找、统计、kiosk 与离线检票，并明确提示多设备离线时存在重复放行窗口。因此，不能仅凭当前材料断言没有现成系统可满足组合需求；应先用具体场景做差距验证。[pretixSCAN 官方指南](https://docs.pretix.eu/guides/pretixscan/android/)
- **Hi.Events 的技术栈需要纠正。** 当前仓库描述使用 Laravel、React、TypeScript 等，之前讨论中的 Vue 表述不准确。仓库提供二维码检票与角色能力，但这些事实不足以证明它已经满足 UniGate 的离线和随行规则。[Hi.Events 官方仓库](https://github.com/HiEventsDev/hi.events)
- **签名不是唯一票证方案。** pretix 文档介绍随机票证 secret 及其他验证方式。UniGate 可比较随机不透明凭证与签名凭证，结合离线名单、撤销与泄露恢复作选择；二维码不应直接承载手机号等个人信息。[pretix 票证设计](https://docs.pretix.eu/guides/ticket-secrets/)
- **全屏不代表设备锁定。** Windows 官方文档将 Assigned Access 等机制用于限制可运行应用；UniGate 的设备方案应按实际平台制定。[Microsoft kiosk 文档](https://learn.microsoft.com/windows/configuration/kiosk/)
- **跨境不等于必然需要安全评估或标准合同。** 网信办规定及 2026 年问答区分主体、数据性质、数量及豁免场景。即便某一出境机制可豁免，也不能据此推导其他个人信息保护义务全部免除。海外访问、名单回传与匿名聚合应分别分析。[2024 年规定说明](https://www.cac.gov.cn/2024-03/22/c_1712776612187994.htm)、[2026 年政策问答](https://www.cac.gov.cn/2026-01/30/c_1771505108953002.htm)

关于微信主体、域名及备案的上一轮具体断言，当前尚未逐条核实，不能直接写入确定约束；待首发地区、部署主体及 H5/小程序路线确认后再查官方要求。
