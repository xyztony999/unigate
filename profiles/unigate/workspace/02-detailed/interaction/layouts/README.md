## 1. 工作人员检票台

手机竖屏依次放置活动与终端状态、扫码区、当前组名额、本次数量、主按钮、辅助入口。主按钮靠近底部；较小屏幕滚动时保持数量与按钮能一起看见，不能覆盖字段或系统安全区。示意采用390 CSS px宽、约844 px高；实现时需适配320 px起的窄屏、缩放及软键盘，不依赖固定整屏高度。

平板横屏采用顶部状态、左扫码、右确认、底部辅助入口。内容区左侧约45%、右侧55%；剩余可入场人数位于右侧最醒目的位置，下方依次为已批准/已入场、本次人数和“确认N人入场”。视口宽度约900 px以上且两区均可容纳触控操作时并排，否则回到手机单列。断点是版式建议，不是设备能力保证。

扫码区仅在READY持续识别。识别成功后停止重复扫描，显示“已识别，扫描已暂停”，进入CONFIRMING；相机画面可淡化为静止提示，不要求继续拍摄现场人脸。未识别时不显示上组数字；保留“请扫码”，不拿示例数或零值冒充已读到的名额。

名额显示“已批准 / 已入场 / 剩余可入场”，避免“总随行人数”等可能与审核后名额不符的标签。本次人数默认1，整数范围1..remainingCount；减号在1禁用，加号在剩余数禁用，数值可直接输入。剩余0改为“本组名额已全部使用”，不展示可提交按钮。确认按钮随数值写成“确认N人入场”；识别不是核销，不自动将剩余数一次性用完。

底部只有“辅助找票”和“本人及本端记录”等获权入口，分别转既有C02/C03；不是把搜索或记录列表叠在扫描区。负责人使用O09时也不把补录、增额、误检更正和凭证补发混在确认按钮旁，这些动作继续去其独立获权工作区。SUBMITTING/UNKNOWN期间不能通过导航绕开当前待核对操作后再扫下一组。

## 2. 自助 kiosk

用户明确要求kiosk横屏，默认采用16:10横屏大触控布局：顶部终端名与检票状态，左侧固定扫码区，右侧为当前步骤提示或人数确认。识别后暂停左侧扫描，右侧展示剩余名额、步进器和主按钮；底部仅保留现场求助入口。横屏是固定平板的设计默认方向，系统级方向锁定仍需部署验证；不保留竖屏优先建议。

待扫码时主文案为“请出示您的入场码”，下方为扫描区及“同组人员可以分批入场”。识别后右侧提示切换为人数确认视图，左侧显示已识别并暂停扫描，主文案变成“这次共有几位入场？”，显示剩余可入场、已批准/已入场、步进器以及唯一主按钮。未提交前可以“暂不检票，返回扫码”，清当前组敏感内存与扫描上下文。

公开屏幕不展示姓名、电话、邮箱、报名参考号、全名单、全场统计或工作人员账号。图中kiosk头部的活动式名称实际绑定`DeviceSessionView.device.name`，示例终端被命名为“新生与家长见面会”；并非从未定义的`eventTitle`字段读取。负责人可在已有终端命名中采用活动简称和入口标识，避免混淆；没有新增读取活动详情或名单的接口。

“需要帮助/联系工作人员”提供本地说明，指引现场求助，不自动发通知、拨号或发送第三方消息。退出kiosk及配置终端走独立管理验证，不放在参与者操作区，也不能靠隐藏按钮或扫码票证解锁。

## 3. 结果与异常的布局切换

新成功以结果面板替换扫码/确认区，醒目显示“允许N人入场”，次要信息为本次登记人数及剩余名额。仅`showAsNewAdmission=true`的新成功触发放行提示；普通确认按钮使用主题色不代表已核销。kiosk成功5秒后清屏，点“完成”立即清；未提交组空闲30秒清屏。

原结果查询或重放使用中性面板，显示“这次操作已经记录，请工作人员核对”，有原时间/人数时按服务端结果展示。没有新绿灯、新放行声音或再次确认核销按钮。

提交中禁用数量、确认、重复扫码和下一组。收到`OPERATION_IN_PROGRESS`仍等待/查询原操作；不能按409一律当失败。明确版本/容量拒绝后才刷新资料，由用户重新确认新动作；资格无效或剩余0不提供放行入口。

UNKNOWN使用“结果待确认，请勿重复扫码或提交”的面板。断联时显示等待恢复；连接恢复且当前身份/组范围有效时，提供或自动执行原ID查询，未查明前不换ID、不清待确认引用、不扫下一组。kiosk恢复需要原组上下文，必要时由工作人员指引重扫原组以查询；重扫不是新的核销。换设备/会话失效则转负责人核对事实。

尚未提交时断网显示“本机暂时无法检票”，不假定存在一次待核对核销；若请求已发出则必须转UNKNOWN。只暂停该端，不能据此把活动全场改为暂停。活动暂停、结束或设备失效展示明确文字，不给确认按钮；活动结束不随网络恢复自动重开。

成功、重放、未知、拒绝的差别必须能从文字读出。提交期间相机不另识别票；结果面板不长期显示上一组资料。后台工作人员核对走其独立授权会话，不在公开kiosk中恢复管理员会话。

## 4. 字段与动作来源

工作人员活动名称来自其获权的`EventList.items[].title`；终端名及有效性来自`DeviceDetail`的`device.name/status/expiresAt`，阶段来自`eventStatus`。联网状态是本机请求/连通性状态，不能仅因系统Wi-Fi图标亮就标“可检票”；设备有效、活动开放且服务可达才进入READY。

当前组名额绑定`TicketResolve → GatePreview.approvedSize/netAdmitted/remainingCount`；`progress`辅助进度文字，`partyVersion`、`scanContextToken`和到期时间用于系统校验，不公开显示。扫码响应无姓名或报名参考号，图稿没有假定这些字段存在。

本次数量绑定`GateCommitRequest.count`；eventId、operationId、expectedPartyVersion、scanContextToken均由原上下文绑定。新结果来自`GateResult.committedCount/remainingCount/committedAt/replayed/showAsNewAdmission`；原结果来自`GateOperation`。图片没有业务接口、二维码秘密、真实相机或模拟联网程序。

P04仍只调用DeviceDetail、TicketResolve、GateCommit、GateOperation四个既有操作。C01/O09继续使用各自既有动作；本次新增静态图稿不增加API或数据访问范围。

## 5. 视觉与触控建议

白底、深色文字及单一深绿色主题；成功/未知/拒绝分别辅以绿色/琥珀/红色，但总有文字。操作目标至少48 CSS px，工作人员主按钮建议高64 px，kiosk主按钮建议高80 px、步进器至少64 px；窄屏与缩放后仍保持可点。正文建议18—22 px，kiosk关键问题28—36 px，人数56—88 px；不让辅助说明抢过人数与主操作。

长活动/终端名可换行或截断并在工作人员端查看完整值，不能挤掉阶段提示。数值键盘、横竖切换、读屏/焦点与颜色对比需在实现后验证；布局图不是可访问性或浏览器兼容性测试结果。Android系统kiosk锁定、摄像头朝向/距离及扫码枪仍需用实际设备确认。
