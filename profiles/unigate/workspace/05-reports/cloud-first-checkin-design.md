## 已确认目标与保留的业务边界

正常检票优先使用公网服务器，异常后支持 Android 热点内的主设备继续处理，另有 Android 备用主设备和浏览器端。公众新增报名、审批占额、修改人数及取消释放在现场期间仍暂停（ADR-032）；这与正常由云端处理核销是两件事，未因最新补充重新开放。

所有写入都受同一个活动级“有效裁决方”约束：正常为云端，接管后为现场主设备。现场负责人可以在两种模式通过当前有效裁决方办理受权的现场加人补录；云端管理页面不能绕过现场接管锁另写名额。

## 拓扑与准备建议

云端提供正常检票 API；Android 主设备在开始前配对、取得完整名单及配置，并准备接收核销记录，备用设备准备副本。用户进一步指出纯云端浏览器页面在断网后入口可能丢失，因此页面供给、核销 API 和局域网必须分别设计，不能只描述“切换接口”。

修正候选为：浏览器从 Android 主设备加载完整的本地可信 HTTPS 页面；正常由该页面请求公网核销 API，负责人确认并满足接管条件后才改用同源本地 API。这样页面刷新不依赖公网，但开始前必须加入现场局域网、验证证书及终端授权，并明确正常跨源访问云端的 CORS/身份。该组合尚未获用户采纳，技术边界及 PWA/独立本地入口替代路线见 browser-entry-continuity.md。

建议在正常阶段就建立可用现场 Wi-Fi，并验证主设备地址和入口；正常请求仍走公网。它是减少故障时重新组网步骤的建议，用户尚未要求所有设备始终接同一热点。普通共享热点、LocalOnlyHotspot、主设备自身蜂窝连接与本地服务绑定分别按机型验证；不假设 LocalOnlyHotspot 自带公网。

## 单一写入方与网络分区

浏览器请求超时可能发生在服务器已提交之后，也可能仅该浏览器网络有故障。不能令每台终端自己判断在线/离线并各自换写入方；否则部分终端在云端、部分在本地会竞争同一名额。

受控切换需要先阻止旧写入方继续有效提交，再验证数据足够完整，最后激活新写入方。手动确认只是操作触发，不是服务器隔离证明；所有已生效的核销都必须覆盖到恢复边界，无法解释的不确定提交应锁住对应名额，不能当成未入场重新放行。

候选机制可以研究活动级写入租约、服务端提交时检查的有效期与代次、数据镜像和持久化回执。这里不预选某中间件，也不宣称加一个租约即可解决安全问题。云端无法联系时，要有提前建立、可验证且云端自行执行的停写约束，或者维持暂停；不能依赖负责人按一次按钮通知到不可达服务器。

租约计时、进程暂停、设备重启、时钟偏差、旧实例提交和恢复后的请求都需纳入机制验证；不把普通设备墙上时钟当成可信裁决。参考：[AWS 关于主节点选举及租约风险的工程说明](https://aws.amazon.com/builders-library/leader-election-in-distributed-systems/)。本项目协议是独立设计提案，不能据该文献声称已经正确实现。

## 数据完整性与成功语义

“定期同步名单”并不能保证接管安全：若云端刚放行一人，本地仍有旧余额，则再次放行会超额。仅在切换时做增量拉取也不能应对切换当时公网已经不可达。

需要在详细协议中选择能证明恢复边界的提交过程：例如云端成功前，对现场可靠副本持久化所需操作或保留记录，明确本地已准备但云端结果不确定的占额规则。该候选会增加正常链路对副本就绪的依赖，需评估吞吐及不可达时的行为，不把“公网优先”解读成任意状态下云端均可先成功再异步补副本。

每个操作有跨两种模式稳定的 ID。超时、切换、刷新均先查询或恢复该 ID，不能用新 ID 自动重扫。绿灯需要对应明确、持久的成功结果；结果待核对时暂停该笔或冻结受影响名额，不能先显示成功后用最终冲突回滚已经发生的放行。

在缺少完整数据或旧写入方隔离证明时，局域网存在不代表可以继续核销。首版不承诺瞬时无感切换或固定秒数；对账、受控等待和异常提示是产品流程的一部分。

## 两种异常切换策略（待选）

1. 异常检测后暂停并提醒，由负责人确认接管（推荐）；系统仍校验单一写入方、数据与不确定请求，不允许人工绕过。
2. 满足隔离、数据完整和所有相关端受控切换条件后自动接管；条件不足仍暂停。它不等于一超时就自动放行，需要更完整的故障判定、滞回及试验。

## 两种公网恢复策略（待选）

1. 已接管的现场继续本地处理到该场结束，恢复网络只用于回传；云端不重新获得核销写权，封存对账后完成交还（推荐）。
2. 网络稳定且负责人确认后，暂停所有端，封存/同步本地操作并核对，令本地写权失效后交回云端；确认完成再恢复。回传成功不等于已经完成回切。

正常故障切换的选择不改变已有“Android 主设备故障需负责人手动切备用设备”（ADR-027）；这是另一类故障流程。

## 待验证场景

- 云端提交成功但回包丢失，之后公网断开；本地接管不再次使用同一名额。
- 一台终端失去公网，其他仍在线；不会两边同时核销。
- 公网抖动、超时、DNS 或认证错误；不因任意错误切为宽松离线模式。
- 云端持续可达但现场副本失联；系统说明是否仍具备可接管保障，不隐瞒复制缺口。
- 主设备或备用设备重启、日志落后，热点重建及浏览器冷打开；未达到就绪状态不能接管。
- 正常恢复后旧主/旧云端会话拒绝写入，待确认操作保持 ID 和结果，不重复累计。
- 审批及来源后台任务在现场期间依旧暂停名额写入；回传不触发旧来源覆盖现场事实。
