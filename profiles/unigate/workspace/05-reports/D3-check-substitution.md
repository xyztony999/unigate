# UniGate 缺失设计检查资产的处理方案

日期2026-10-21；版本v1.0；状态：用户已选择1采用本项目检查方案（ADR-043）；下文原方案及选项保留为审阅历史。项目检查取代缺失原版资产的文件前置要求，但不取消机械/人工核对或独立Gate1。

## 已完成与发现

原版`prd-to-api-design/template.md/check.sh/checklist.md`在已安装插件、用户技能目录、本机引擎源码仓及其可查历史中均未找到。未修改或重装全局插件，未把同名自建文件伪装成原版。

进一步读取已安装引擎`payload/skills/validation/SKILL.md`，找到164条内嵌D3检查要求：CH1为12条、CH2为4条、CH3为16条、CH4含细分项87条、CH5含细分项23条、GL为22条。原文条目及SHA256见[D3-check-source.json](D3-check-source.json)。这些条目不是新编造的126+项原版清单；其中CH6的3条定义及GL-013—020、GL-023—025共11条定义仍不可得。

引擎说明本身将技术规约交由激活栈提供，并声明SCM采购案例只作参考；本项目使用Spring Boot/Vue通用Web栈。因此不能为满足参考检查强加MySQL/InnoDB、采购公司/物料字段、特定MQ、pageNum、key/value或ScmCardPage，也不能把真实适用要求一律标“不适用”。

## 建议的项目验收依据

以引擎现有D0—D4方法论、激活`springboot-vue-web`的API/页面/验证规约、已确认ADR及项目检查清单作为本项目设计验收依据；缺失的原版脚本及未定义条目保留缺失记录，不再作为文件存在性阻塞项，不声称原版全条目通过。

继续保留强制的“机械检查→人工核对”两步。项目机械工具已落盘并执行：[工具说明](../../../../tools/design/README.md)，[31项实际结果](D3-project-check.json)；它不是完整OpenAPI/JSON Schema验证器。下表为本轮实际人工核对的项目要求及证据，不代替164条原文逐条通过，也不是数据库/HTTP运行测试。

| 项目要求 | 实际核对证据 | 结果/适配说明 |
|---|---|---|
| 背景、边界、对象 | PRD1—3，API1、4.1，领域模型 | 覆盖五角色/两条来源路径；业务对象不扩大 |
| 容量和组余额 | API2.1—2.2，数据设计4.1—4.3 | 批准/增额/导入同库强事务；不套用参考MQ最终占额 |
| 活动及审核状态 | API2.1、EventTransition/ReviewDecide | OPEN冻结公众变更，待审不占额，差额审批保留原名额 |
| 写入幂等及未知结果 | API2.3、4.5、GateCommit/GateOperation | 同ID补查，重放不再次放行；未查明不另发核销 |
| 匿名身份连续性 | API3.2.1，CsrfView及ANON写请求头 | 新clientContextId不能自动套用旧操作，防止误建新组 |
| 本人授权可见 | MyGrantList，FL-R-002 | 补齐既定功能；不接受他人accountId，不开放全局授权列表 |
| 最小字段/角色权限 | API3.2、PartyView、GateCandidate | 服务器字段投影；kiosk不能搜索；管理员无默认名单权 |
| 检票员记录范围 | AuditList/GateRecords/OperationResult | 本人或经当前cookie验证的本端，不能凭传deviceId扩权 |
| 导入与重复核对 | API3.3、BatchPreview/DuplicateResolve/BatchCommit | 同源防重，跨源人工；选中行全提交或全回滚 |
| 凭证及恢复 | API3.2，CredentialReissue/RecoveryVerify | 查询/变更/入场分离，补发不重置核销 |
| 纠错与审计 | GateCorrect，数据设计4.4 | 追加关联更正，everAdmitted保留，不变离场功能 |
| 响应/分页/枚举 | API3.1、4.3、枚举池 | 采用本栈code/label与page；不用参考key/value、pageNum |
| SQL、索引与关系 | 数据设计1—5 | UUID/PostgreSQL设计候选；无虚构执行结果，不加无需求组织字段 |
| 外部及通知 | API3.3—3.4，连接器可行性报告 | 真实权限未验证仍如实保留；邮件失败不撤资格 |
| 导出与清理 | API3.4，数据设计5 | 独立导出权、限时下载、实际处置/备份恢复；不用软删除冒充清理 |
| 版本与追溯 | API6、OpenAPI0.2.0，ADR-042 | 修正既定功能缺口；不把选择1解释为代码或上线授权 |

在该方案获得采用后，D3可按项目适用清单完成归档，再开展D4字段级PageSpec。D4同样使用本栈页面规约进行机械/人工检查；覆盖路由、角色、字段、按钮/API、状态、异常及触控要求，不要求缺失的SCM原版文件或专用组件。Gate1仍须独立执行并记录真实结果，不因采用本方案直接通过。

## 已准备的后续工作

已根据采用的合同整理[页面准备清单](page-preparation.md)，仅列页面入口与已有操作的对应，不作为正式PageSpec或D4完成证据。正式D4仍需确认模块信息、查询条件、列、按钮权限、表单分组、详情区块和页面类型七项，可集中审阅。

## 处理方式选择

1. **采用以上项目检查方案（推荐）**：明确不再让缺失的原版资产阻塞本项目，完成适用检查后继续页面设计；保留缺失记录，仍执行机械/人工检查及Gate1。
2. **保留原版资产为强制前置**：先恢复完整原版模板、脚本和清单，再继续正式D3/D4；当前合同及项目检查成果保留。

确认原因：已启用设计技能要求“先跑机械脚本（check.sh），再逐条人工核查（checklist.md）。两阶段均为强制，不可跳过任一阶段。”本方案改用可追溯的项目验收依据，需由用户明确选择；此前采用API不自动表示放弃该要求。
