# UniGate 浏览器现场检票可行性与方案提案

最新范围：ADR-039 确认在线首版。本文局域网 HTTPS、主备和热点兜底方案后置；相机的安全上下文与浏览器兼容性要求仍适用于公网 HTTPS 页面，不能整页解释为首版待办。

日期：2026-10-20；依据 ADR-035；状态：官方资料核实及待验证方案，不是设备实测结果或已批准技术选型。

最新变更：ADR-036 确认正常优先连接公网服务器，网络异常后才切 Android 热点及主设备。本文的本地同源 HTTPS 为兜底入口候选，不再代表始终本地裁决；“两种组网候选”保留对照，当前优先 Android 热点。受控切换与数据条件以 cloud-first-checkin-design.md 为准。

## 官方事实

1. 相机能力入口 MediaDevices 被规范限定为安全上下文。普通局域网 IP 的 HTTP 页面不能作为摄像头扫码的可靠上线方案；另一台设备的服务不因其位于同一 Wi-Fi 而成为浏览器本机 localhost。参见 [W3C Media Capture and Streams，9.1/9.2](https://www.w3.org/TR/mediacapture-streams/#navigator-interface-extensions)。
2. Chrome 官方文档说明 Local Network Access 已替代此前的 PNA 方向，权限请求限于安全上下文；其初始限制针对公网到局域网/回环的请求，并计划扩大范围。不能继续一概断言任何 HTTPS 页面访问局域网 HTTP 都必然被混合内容规则阻断，也不能把有条件豁免解释为跨浏览器可靠部署路径。参见 [Chrome LNA 说明](https://developer.chrome.com/blog/local-network-access)。该页面包含历史版本阶段的限制，不以历史未覆盖某协议视为当前通用保证；具体版本参见 [Chrome 145 发布说明](https://developer.chrome.com/release-notes/145)。
3. Let's Encrypt 的 DNS-01 可验证其 Web 服务未公开在互联网的域名，但 DNS-01 不验证 IP 地址；签发与续期需要在具备互联网条件时完成域名控制验证。参见 [Let's Encrypt Challenge Types](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge)。
4. Android LocalOnlyHotspot 可用于同网设备通信，不提供互联网访问；它的用途与普通互联网共享热点不同。所需权限、系统版本和设备行为应按目标机型验证。参见 [Android local-only hotspot](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot)。

## 推荐候选：本地主设备同时提供页面和接口

以下为基于上述事实的设计推论，尚未实现或实测。

Android 主设备内置局域网 HTTPS 服务，提供打包的 Vue 检票静态资源及同源本地 API。浏览器从该设备加载页面，全部现场必需资源随包提供，不引用现场必须联网加载的字体、扫码库或 CDN。只有云端报表、外部连接和通知等能力依赖公网；本地检票不依赖云端页面持续可达。

同源方案减少公网页面跨源访问局域网接口的复杂度，但不意味着自动免除浏览器/操作系统权限。验收必须覆盖首次打开、刷新、断公网后重新打开和已有终端恢复。缓存仅作辅助，不能只用活动开始前曾打开过页面来证明可离线运行。

工作人员端需经预配对、登录/会话验证及活动范围授权；公共可访问的本地服务器不等于名单公共可读。kiosk 仅使用组码解析所需最小结果，不预载完整名单。凭据不放在可长期传播的 URL 查询参数中；票码不能换取管理员权限。

## 两种组网候选

### 方案 1：独立便携路由器（当前推荐，待选择）

主备设备及检票端加入独立 Wi-Fi，路由器负责网络，不承接业务数据库或核销裁决。活动前确认终端互通、无 AP/访客隔离、地址分配及本地域名解析；主设备仍为 Android，不增加必须携带电脑的要求。

优先研究活动专用域名、预先签发的可信证书及路由器局域网 DNS 将域名指向主设备的组合。该组合需要可配置路由器、有效证书、正确设备时间及目标浏览器信任链；它是设计候选，不是对任意路由器免配置或任意断网证书验证行为的保证。DoH/Private DNS、DNS 重绑定防护与 DNS 缓存都可能影响解析，须逐台验证；接管后 DNS/入口切换也必须验证。

每台主备设备宜独立生成并保护服务私钥，证书按实际接管入口准备，避免把共享长期 TLS 私钥硬编码进所有 App。域名 DNS 的管理密钥保留在签发管理侧，不随检票页面或设备分发。活动前检查证书有效期、完整链及设备时间，现场不依赖临时联网续签。

### 方案 2：Android 热点（轻便候选，待选择）

使用安卓设备创建现场热点，需确认主备及浏览器端能互相访问、本地 HTTPS 域名/地址与证书可信且匹配、主设备续航及持续运行。不能假定普通热点可自定义 DNS 或固定网关地址。

若热点无法提供所需域名解析，可研究预配置的可信证书/本地信任方案；如需安装组织根证书，应明确适用设备、信任范围、安装/移除和私钥管理，不将“点击忽略证书错误”作为安全上下文或相机可用性的证明。该路径未完成验证前，不承诺手机热点零配置支持全部浏览器。

热点与主设备同机时，其故障同时影响网络和业务；接管需先恢复网络，再确认有效主及日志，再重新连接终端。独立路由器把这两项故障分开，但不解决业务层防双主问题。

## 不确定请求与接管

每次核销沿用唯一操作标识，由有效主设备持久化后返回。浏览器超时、刷新及切换主设备时必须保留尚未确认操作的标识并查询原结果，不自动另发一笔。终端的少量待确认元数据须限定有效期并能在登出/活动结束清理；不得因此持久缓存全量个人名单。

暂停与切主不能只靠改变 DNS，旧主自带核销端也必须失效。主备日志确认边界、旧主隔离、有效会话代次及所有核销端重新绑定在技术架构中共同设计；网络故障时不允许两边独立继续放行。

## 待执行验收

- 首轮建议 Android Chrome 与 Windows Chrome/Edge；iOS/Safari 等支持范围待真实目标需要及实测决定，不把“浏览器端”解读成全平台已适配。
- 断开公网但保留 Wi-Fi，浏览器重新打开页面、授权相机、完成核销；目标配置不依赖禁用浏览器安全功能。
- 拒绝/撤销相机、本地网络权限，证书过期、设备时间错误、解析失败、Wi-Fi 自动切换等均能明确阻止核销并提示恢复路径。
- 两个浏览器/原生端同时核销最后名额，只成功一次；超时后查询原操作，不多放一人。
- 主设备故障，暂停、隔离旧主、核对并恢复备用设备；全部端统一绑定，不确定请求得到核对。
- kiosk 清屏、管理解锁、受限搜索与字段验证；操作系统层锁定独立验收，网页全屏只算显示方式。

## 结论边界

浏览器需求纳入首版设计；可信离线入口及目标机型需验证，尚无设备实测或可部署的证书配置。选组网方式决定优先实现和验证路线，不是宣称另一种方式永不可行；不进行设备购买、域名购买或账号授权。
