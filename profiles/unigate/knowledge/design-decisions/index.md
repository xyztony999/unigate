## ADR-002：按组名额分批入场

- 日期：2026-10-20。
- 背景：需要兼顾随行人员分批到场与简单报名体验。
- 来源：用户对随行入场方式选择“1”。
- 决策：同组共用一个报名码，允许分批到场；每次核销实际入场人数，剩余名额供后续使用，无需逐一登记随行者身份。
- 示例：一组 3 个名额，首次入场 2 人，剩余 1 个名额；稍后核销最后 1 人。
- 影响：设计必须区分组总名额、累计已入场人数与剩余名额。组码只管理名额与数量，不提供逐人身份核验或逐人防重复能力。
- 未决定：主报名者是否必须在场、现场增减名额权限、超额处理、撤销误检、离场及再次进入；这些不能从本次选择中推定。

## ADR-003：多设备同时离线检票

- 日期：2026-10-20。

- 来源：用户对断网可用范围选择“3”。

## ADR-005：离线自由入口与同步后人工处理冲突

- 日期：2026-10-20。

## ADR-018：待审核不占额，通过审核时占额

- 日期：2026-10-20。
- 来源：针对待审核名额“提交时预占 / 审核通过时才占”，用户回复“2”。

- 影响：名单准备、现场主设备性能和同步设计以该规模验证；每场活动仍按实际容量配置，不把 500 写成全部活动统一的报名额度。
- 边界：该人数是计划参与规模，不等于数据库最多只能存 500 条记录；待审核、拒绝、取消、来源及检票审计记录需另行估算。尚未通过性能或设备实测。
- 未决定：同时检票设备数、入场峰值、入口分布与无线覆盖、具体 Android 机型及系统版本。

## ADR-020：同时 2–5 台设备检票

- 日期：2026-10-20。
- 来源：针对同时检票设备数“2–5 台 / 6–10 台 / 超过 10 台”，用户回复“1”。
- 决策：首版按单场同时 2–5 台设备检票设计；主设备如参与扫码也计入台数。
- 影响：结合 ADR-019 的 500 人以内目标，验证多设备争抢同组剩余名额、请求重试和主设备持续运行。该选择不代表已经实测支持 5 台，也不等同于 5 个物理入口或 5 个独立热点。
- 未决定：具体机型、到场峰值、无线覆盖、工作人员或参与者自助模式，以及主设备故障时的处理。

## ADR-021：工作人员与参与者自助检票均支持

- 日期：2026-10-20。
- 来源：针对操作模式“工作人员 / 自助 kiosk / 两种都支持”，用户回复“3”。
- 决策：首版同时支持工作人员扫码检票与参与者在固定平板上自助检票；平板可切换自助模式。
- 工作人员模式：扫码、确认本次人数及辅助查找报名；完整字段可见范围和高权限操作另行设计。
- 自助模式：通过报名码识别本组、选择本次入场人数并提交，限制名单搜索和个人信息展示，异常转工作人员处理。自助不能凭手机号尾号搜索或展示其他组资料。
- 影响：两种模式共享现场主设备的名额核销逻辑；终端锁定、管理解锁、清屏与人数校验需进入交互设计。自助确认代表人数申报，不代表自动识别实际通过的自然人数。
- 未决定：现场补录和临时加人的权限、撤销误检、离场再次入场、主设备故障及无凭证找票流程。

## ADR-022：现场加人与补录仅负责人可办理

- 日期：2026-10-20。
- 来源：针对现场加人与补录“检票员可办理 / 仅负责人 / 首版不支持”，用户回复“2”。
- 决策：允许现场临时增加随行人数以及为未报名者补录，但仅活动负责人可办理；普通检票员转交负责人，自助端不提供此类操作。
- 影响：负责人权限与普通检票权限明确区分，后台及现场端均需校验权限；操作受剩余人数额度约束，并保留操作人、时间及人数变更记录。不能通过反复同步外部名单绕过此权限。
- 约束：增加组名额与当次实际入场核销是不同业务动作，不因名额增加自动计入到场人数；仍需满足活动的有效入场资格与容量规则。
- 未决定：现场补录在审核模式中的具体确认交互、已入场后取消/减额、误检撤销及再次入场规则。该选择不等于负责人可无约束突破活动额度。

## ADR-023：每个名额只核销一次，不记录离场

- 日期：2026-10-20。
- 来源：针对离场及再次入场“每名额只核销一次 / 登记进出 / 按活动配置”，用户回复“1”。
- 决策：首版每个报名名额只核销一次，保留同组分批入场能力；不记录离场，不提供离场后再次入场的业务模式。
- 影响：组剩余名额只在有效入场核销后减少；不能通过所谓离场释放已使用名额。报表展示累计入场人数，不展示当前在场人数。
- 边界：系统按组人数记账，仍不宣称能逐人识别真实自然人。误操作撤销/更正应单独设计为有权限、有审计的纠错动作，不能作为再次入场功能或随意恢复名额的入口。

## ADR-024：手机号短信验证按活动配置

- 日期：2026-10-20。
- 来源：针对短信验证“不需要 / 填写手机号必须验证 / 按活动配置”，用户回复“3”。
- 决策：首版手机号短信验证按活动配置，默认关闭，主办方可开启。
- 影响：未验证模式保持免登录提交体验，不把联系方式当作已验证身份。开启验证时需启用手机号字段，完成验证后才能通过相应报名校验；不能发布“关闭手机号但要求短信验证”的冲突配置。具体必填约束和变更行为在规格中明确。
- 边界：验证手机号不等于识别组内全部随行者，也不等于建立跨活动唯一人员身份；外部导入的手机号不能自动标记为已在 UniGate 验证。
- 未决定：短信服务商、有效期、限流及失败重试、凭证领取/找回、审核通知方式。验证短信与报名通知是独立用途，本次未确认需要主动发送领票通知。

## ADR-025：页面领取入场码并通过电子邮件通知

- 日期：2026-10-20。
- 来源：针对“仅页面领取 / 页面加短信通知”，用户回复“1和通过电子邮件通知”。
- 决策：提供私密报名状态/领票查询链接，参与者可保存并查看状态及入场码；同时支持电子邮件通知领取。短信仍按 ADR-024 用于可选手机号验证，本次未选择短信领票通知。
- 字段影响：邮箱成为第四个报名基础字段，需纳入内置表单与外部来源映射，扩充 ADR-015 的基础字段范围；启用/必填策略尚待本轮后续澄清，不扩展任意问卷编辑器。
- 资格约束：审核模式未通过时页面仅显示状态，不提供有效入场码；邮件中的领票路径也不能绕过审核或票证有效性检查。
- 交付原则：邮件发送情况与报名资格、票证状态区分，邮件失败不自动撤销已成功的报名，参与者仍可使用已保存页面。具体通知触发点、模板、发件配置、队列重试及邮箱更正待设计。
- 范围：本次仅确认系统通知需求，不授权本会话实际向参与者或校方发送邮件；也不自动将海外名单文件邮件交付纳入此次领票通知功能。

## ADR-026：邮箱按活动配置启用与必填

- 日期：2026-10-20。
- 来源：针对邮箱“按活动配置 / 全部必填 / 始终选填”，用户回复“1”。
- 决策：邮箱与其他基础字段一样，由主办方按活动配置启用与必填；未启用或未填写时参与者仍通过私密查询页面领取和查看状态。
- 影响：报名、导入和邮件通知需遵循邮箱字段配置。选填字段不能因未提供邮箱阻断有效报名；邮件发送状态与报名资格分离，不将邮箱作为唯一必须存在的身份标识。
- 承接：解决 ADR-025 的邮箱配置未决项，扩展后的基础字段为姓名、手机号、邮箱、随行人数；仍不做完整问卷编辑器。邮件触发、验证与更正等细节在后续规格中明确。

## ADR-027：负责人切换备用主设备后恢复检票

- 日期：2026-10-20。
- 来源：针对主设备故障“暂停等原设备 / 备用主设备接管 / 终端独立继续”，用户回复“2”。
- 决策：首版支持备用主设备接管，由活动负责人切换并完成数据核对后恢复检票。
- 影响：接管期间暂停核销；需要预先配置备用设备和数据准备机制。恢复前核对有效报名、已核销名额及不确定提交，不得仅用活动初始名单重新开始。
- 单一主设备约束：同一现场会话在同一时刻只允许一个有效主设备核销。需设计旧主设备失效、终端重新绑定和旧主设备恢复后的隔离/合并流程；不将手动切换等同于已解决双主问题。
- 范围：不承诺自动无缝切换、零数据丢失或固定恢复时间；主备同步方式、数据核对来源及不可恢复时处理在 D1-D4 明确。原主设备同时承担热点时还需恢复现场连接。
- 承接：解决 ADR-006 中主设备故障兜底方向；不选择终端独立放行后容忍超额的降级模式。

## ADR-028：后端 Java / Spring Boot，前端 Vue

## ADR-029：个人明细保留期限按活动配置，默认 30 天

- 日期：2026-10-20。
- 来源：针对活动后明细保留“固定 30 天 / 固定 90 天 / 按活动配置默认 30 天”，用户回复“3”。
- 决策：UniGate 管理的报名个人明细按活动配置保留期限，默认从活动结束后保留 30 天。到期进入清理流程，私密查询/领票页面有效期需与之对齐；不含个人标识的汇总统计可独立保留。
- 影响：生命周期设计覆盖服务器主数据、现场主备及检票端副本、导入暂存和系统生成的导出文件；配置变更应可追溯。不能只隐藏前端记录或标记逻辑删除就视为完成清理。
- 设计边界：离线设备到期访问控制、恢复连接/下次启动后的实际清理，备份轮换及恢复后防止旧数据复活，均需在 D1-D4 明确。当前未定义瞬间清除全部离线介质和备份的保证。
- 外部副本：接收方已下载文件、已投递邮件及第三方平台原始名单不受 UniGate 直接删除控制；接收主体的保存责任与交付约定需单独说明。
- 未决定：保留天数允许范围、活动结束时间字段、时区与清理任务窗口等技术细节。30 天为用户选择的产品默认，不据此得出所有场景的法律统一保留期限。

## ADR-030：报名后自助修改与取消按活动配置

- 日期：2026-10-20。
- 来源：针对报名后变更“截止前自助 / 仅负责人 / 按活动配置”，用户回复“3”。
- 决策：主办方按活动配置是否开放参与者自助修改随行人数和取消报名；现场临时加人仍仅负责人办理（ADR-022）。
- 影响：页面查询与变更权限区分，变更需符合截止时间、名额、资格和状态规则；取消与额度释放需在完整状态机定义，不能直接删除已存在的检票事实。
- 待设计：开关默认值、截止时间、增加人数是否重新审核、已有核销后的变更限制，以及查询凭证与变更能力的隔离。这些属于需在后续规格集中审阅的规则，当前未虚报已确认。

## ADR-031：后台准备后，现场 Android 独立检票

- 日期：2026-10-20；来源：用户集中回复“A1 B1 C1”中的 A1。
- 决策：后台完成活动配置、名单导入和现场准备；Android 主设备在现场断公网后仍可在局域网内提供检票及统计。
- 边界：不要求首版 Android 单机从零建活动、导入文件并替代全部后台；外部名单路径无需使用内置报名。设备必须事先完成有效数据和权限准备，只有缓存旧名单不代表可以启动现场。
- 承接：明确“独立运行”的范围；不改变局域网单主、主备接管及容量约束。

## ADR-032：现场会话启动后冻结云端名额写入

- 最新适用范围：ADR-036 将检票裁决改为公网服务器优先、故障后切现场主设备。本条关于现场期间暂停云端新增报名、审批、改人数及取消释放的规则继续保留；“云端连网也不核销、现场始终本地裁决”的旧推论被 ADR-036 替代，不以本条禁止正常云端检票。
- 日期：2026-10-20；来源：用户集中回复“A1 B1 C1”中的 B1。
- 决策：现场检票启动后，暂停云端新增报名、审核占额、人数修改、取消释放等影响资格与名额的操作，交由现场负责人通过有效主设备处理。
- 边界：联网也不恢复云端并行写入；云端可保留只读查询和标有同步时间的统计。外部平台仍可收集答卷，但不得自动形成有效名额。通知重试不属于名额写入。
- 设计要求：现场启动必须有云端冻结确认和一致的数据版本，之后才能断公网；现场结束后先封存并对账，再决定是否恢复云端写入。具体交接协议、失败状态和解冻条件留待规格设计，不能从“冻结”推导已解决接管或双主。
- 权限：工作人员正常核销不受影响；现场资格和名额调整仍仅负责人。暂停期间的云端取消请求不能先释放名额、随后才通知现场。

## ADR-033：负责人按来源配置外部名单审核属性

- 日期：2026-10-20；来源：用户集中回复“A1 B1 C1”中的 C1。
- 决策：负责人在文件导入预览或平台连接配置时，将来源明确设为“已获入场资格名单”或“待审核名单”。前者通过校验且容量允许后生效发码；后者审核通过才占额发码。
- 校验：有效来源不能绕过活动范围、字段、容量、来源幂等及冲突检查；第三方任意字段不能自行授予入场资格。现场阶段遵循 ADR-032，来源后续更新不得直接修改现场名额。
- 待设计：批次提交的原子边界、源记录更新及撤回、跨来源疑似重复的人工处理。来源配置不等于已验证个人账号 API 权限。

## ADR-034：五类角色，允许同账号兼任

- 日期：2026-10-20；来源：角色与设备批次用户回复“A1 B2”中的 A1，不与前批编号混用。
- 决策：系统管理员、活动负责人、检票员、校方只读人员、参与者，共五类。管理员管理部署、账号及连接凭据；负责人管理获授权活动的配置、名单、审核、现场异常及导出；检票员查找与核销；校方仅按活动和字段授权查看；参与者限本组。
- 边界：同账号可兼任管理员与负责人。系统管理员身份不自动授予全部活动明细的应用层读取权限；这不表示部署运维人员在基础设施层绝对无法接触数据。校方只读与管理员代为导出仍分开授权。
- 自助 kiosk 是受限终端模式，不是新建的名单浏览角色。现场加人补录权限保持仅负责人。完整动作矩阵与菜单分配在 AA/FL 中按本边界展开。

## ADR-035：Android 主备设备，另支持浏览器检票端

- 最新路由：按 ADR-036，正常优先连接公网检票服务；异常后才受控切换至 Android 主设备。本文要求浏览器支持局域网工作，是故障兜底能力，不要求始终本地裁决。
- 日期：2026-10-20；来源：角色与设备批次用户回复“A1 B2”中的 B2。
- 决策：主设备及备用主设备采用 Android App；其他现场检票设备需支持浏览器操作。管理后台、报名领票仍为 Vue Web 方向。
- 边界：不将浏览器端降为必须联网访问云端的端；应在现场断公网、局域网可用时连接有效 Android 主设备。浏览器端不独立充当主设备或独立分配名额。
- 待验证：可信 HTTPS、局域网连接及相机权限、静态资源供给、终端授权、接管后连接及不确定请求恢复。具体 OS/浏览器验证矩阵、证书与组网方案未由该选项自动锁定；不能承诺任意浏览器兼容。
- 范围：不扩展 iPad 主设备，不固定 Android 开发语言；纯网页全屏不等于操作系统层 kiosk 锁定。

## ADR-036：公网服务器优先，异常后切 Android 热点现场方案
